# Step-by-Step Plan: Migrating a Monolithic Postgres to a Sharded Architecture (Zero Downtime)

## Phase 1: Assessment & Design (Weeks 1–3)

### 1.1 Inventory the Monolith
- Map all tables, their sizes, and access patterns (read-heavy vs. write-heavy)
- Identify hot tables and high-latency queries
- Document current indexing strategy, foreign keys, and constraints
- Measure peak traffic windows and query distribution

### 1.2 Choose a Sharding Strategy
- **Key-based sharding** (most common): partition by a natural key (e.g., `tenant_id`, `user_id`)
- **Range-based sharding**: partition by date ranges (good for time-series data)
- **Hash-based sharding**: distribute evenly across shards
- **Geographic sharding**: route requests based on user location
- Decide on **shard count** (start with 4–8, scale later)

### 1.3 Design the Target Architecture
- Decide between **horizontal sharding** (split tables across shards) vs. **vertical sharding** (split tables by domain)
- Choose a sharding middleware: **PgShard**, **Citus**, **PostgreSQL with pg_partman**, or **Vitess**
- Plan for **cross-shard queries** (join queries across shards)
- Design the **routing layer** (proxy or application-level routing)

### 1.4 Define the Migration Window
- Target a low-traffic period (e.g., weekend)
- Plan for **dual-write** and **dual-read** periods
- Estimate total downtime (target < 5 minutes for cutover)

---

## Phase 2: Build the Sharded Infrastructure (Weeks 4–6)

### 2.1 Provision Shards
- Create N shard databases (or use a managed service like Citus Cloud)
- Set up connection pooling (PgBouncer recommended)
- Configure replication for each shard (streaming replication)

### 2.2 Set Up the Routing Layer
- Deploy a **proxy** (PgBouncer, PgShard, or Vitess) that routes queries to the correct shard based on the sharding key
- Configure health checks and failover

### 2.3 Build the Migration Tooling
- Write a **data migration script** (custom ETL or use tools like **AWS DMS**, **Debezium**, or **pg_dump/pg_restore**)
- Build a **dual-write service** that writes to both monolith and shards
- Build a **dual-read service** that reads from both sources
- Create a **consistency checker** to validate data between monolith and shards

---

## Phase 3: Initial Data Migration (Weeks 7–8)

### 3.1 Full Load
- Perform an initial full load of data into shards
- Use **parallel loading** to speed up large tables
- Verify row counts and checksums match between monolith and shards

### 3.2 Start CDC (Change Data Capture)
- Set up **CDC** (e.g., **Debezium**, **pglogical**, or **AWS DMS**) to capture changes from the monolith
- CDC feeds changes into shards in near real-time
- Verify CDC latency is < 1 second

---

## Phase 4: Dual-Write & Dual-Read (Weeks 9–12)

### 4.1 Enable Dual-Write
- Modify the application to write to **both** the monolith and shards
- Use a **write-through** pattern: write to monolith first, then async to shards (or vice versa)
- Handle **write conflicts** (e.g., last-write-wins, or use vector clocks)

### 4.2 Enable Dual-Read
- Route reads to **both** sources
- Start with **read-heavy** traffic first (easier to validate)
- Gradually increase read routing to shards

### 4.3 Validate Consistency
- Run **consistency checks** continuously (row counts, checksums, spot checks)
- Monitor for **data drift** between monolith and shards
- Fix any inconsistencies before cutover

### 4.4 Performance Testing
- Run **load tests** against shards to ensure performance meets SLAs
- Identify and fix **slow queries**
- Tune indexes and query plans

---

## Phase 5: Cutover (Week 13)

### 5.1 Pre-Cutover Checklist
- Confirm CDC is caught up (no lag)
- Run a final consistency check
- Notify stakeholders
- Prepare rollback plan

### 5.2 Execute Cutover
1. **Pause writes** to the monolith (or switch to read-only)
